RESEARCH EVOLUTION & KEY FINDINGS

Community research identified several important findings about parameter extraction:

Spring 2026 Baseline:
- Parameter extraction pipeline produced 346 candidate names
- Grounding against 185-parameter gold set showed challenges with WARL classification
- Cross-model agreement on new parameters was low (Jaccard ~3.8%)
- This baseline helped define the scope of undecidable cases

Key Findings from Research:
- 26 entries labeled NORM_CSR_WARL in Spring 2026 gold set
- 4 confirmed decidable by schema pattern
- 4 stale (already migrated to new schema in #2090)
- 18 not decidable from syntax alone
- This motivates Layer 2 validation: focus on decidable cases

Schema Evolution:
- 9 parameters already use type: array + items.enum encoding
- PR #2090 migrated 4 stale parameters into this pattern
- Repository itself validating the approach: migration was intentional

ALLEN BAUM'S GUIDANCE (Slack - Latest Clarifications)

Allen clarified the actual focus and schema patterns:

On Parameter Identification:
"I think the focus is primarily to find parameters. WARL are obvious cases."
"The WARL schema is primarily to be able restrict the values that will be tested."

On Schema Patterns:
"The schema that we've proposed is mask:value{;state}, range_hi:range_lo, and enum."
"There are two classes of enum: a bitmask whose bit position encodes the value, 
and a struct which has a size field, and an array of that size where each element 
is the value."

On Scope:
"If we have to classify something by hand for 18 undecidable cases, I think that 
level of effort is completely in the noise."
"There aren't so many WARL fields that we can't fill in those details by hand if need be."

On Conditional Parameters:
"Sometimes a WARL field isn't explicitly labelled WARL, but become one under 
certain contexts (e.g a RW field may become RdOnly0, which means the set of 
legal values change."
"That makes this bit functionally WARL, and thus needs a parameter value."

On Parameter Scope:
"I don't think we even care that an LLM extracts the valid combinations 
(though there should be code to validate it somewhere). We care that it 
identifies the legal parameter(s)."

WHAT SURVIVES FROM THIS RESEARCH

✓ Three-way classification (absent extension / cardinality condition / predicate) is correct framework
✓ Schema-shape keying finds flat cases (but not all cases)
✓ Layer 2 CSR-context validation is valuable for identifying decidable subset
✓ Hand classification for edge cases (18 items) is completely acceptable
✓ Research focus should be on identification, not combination extraction

---

WHAT CHANGED

✗ Not all WARL fields are "type: array" encoded
✗ Focus is not on schema-shape pattern matching
✗ Focus is on parameter IDENTIFICATION first, encoding second
✗ Multi-parameter dependencies should be identified, not decoded
✗ Goal is not to extract all valid combinations

---

FOR FALL 2026 WORK

Realistic Three-Tier Approach:
1. Identify parameters (LLM extraction)
   - Which fields have legal-value constraints?
   - Classify: WARL, conditional WARL, conditional RW, etc.

2. Classify schema type (LLM + expert)
   - Enum (1-64 values): list them
   - Mask:value{;state}: identify condition
   - Range_hi:range_lo: set bounds

3. Validate & refine (expert review)
   - Manual review for undecidable cases
   - Build validation code
   - Refine based on spec text

This is grounded in community research and aligned with Allen's actual guidance.
