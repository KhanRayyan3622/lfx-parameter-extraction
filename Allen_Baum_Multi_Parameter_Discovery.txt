ALLEN BAUM'S GUIDANCE ON PARAMETER IDENTIFICATION & SCHEMA
Documented: August 1, 2026 (Latest clarifications from Slack)

---

CORE PRINCIPLE: FOCUS ON PARAMETER IDENTIFICATION, NOT COMBINATIONS

Allen Baum clarified the actual goal:
"I think the focus is primarily to find parameters. WARL are obvious cases. 
The WARL schema is primarily to be able restrict the values that will be tested, 
since (depending on the size of the field) the list can be ... large."

What matters: Identifying what IS a parameter
What doesn't matter: Extracting all valid combinations of conditions

---

THE THREE SCHEMA PATTERNS FOR LEGAL VALUES

Allen proposed three schema patterns for encoding legal-value parameters:

1. ENUM (Discrete Values)
   - List of 1-64 legal values
   - Two encoding classes:
     a) Bitmask: bit position encodes the value
     b) Struct: size field + array of that size
   - Example: {BARE, SV39, SV39+SV48, SV39+SV48+SV57}
   - Works well for most cases

2. MASK:VALUE{;STATE} (Conditional Values)
   - Format: mask:value pair, optionally with state condition
   - Used when legal set depends on architectural state
   - Encodes the condition that determines legality
   - Example: 16-bit bitmask with conditional nesting

3. RANGE_HI:RANGE_LO (Address Ranges)
   - For fields wider than 64 bits
   - Used for address-like legal values
   - Would need array of 2^57 elements if encoded as full enum
   - More practical to express as range constraints

---

CRITICAL CLARIFICATION: THE 9 PARAMETERS WITH TYPE:ARRAY

Allen: "Look closer. That is really an enum pattern, which is technically 
a list of legal values, and that doesn't work everywhere."

This means:
- The 9 existing array parameters ARE using enum encoding
- But enum encoding only works for values 1-64 in size
- Wider fields need range_hi:range_lo pattern instead
- Don't key on "type:array shape" - key on parameter identification

The real lesson: Focus on identifying which fields ARE parameters, 
then encode them using the appropriate schema (enum, mask:value, range).

---

HGATP.MODE: CORRECT INTERPRETATION

Allen: "I don't think I was the one that said hgatp.MODE pulls from 5 parameters."

Correct interpretation:
- hgatp.MODE encodes virtual memory address-space translations
- Legal values follow nested-subset constraint: 
  * If SV48 is legal, then SV39 must also be legal
  * If SV57 is legal, then SV48 and SV39 must be legal
- Also constrained: cannot be superset of SATP (hypervisor constraint)
- Encoded as: 16-bit enum bitmask with bits set for {BARE, SV39, SV39+SV48, SV39+SV48+SV57}

What matters: hgatp.MODE IS a legal-value parameter
What doesn't matter: Extracting all valid combinations from prose
The LLM should identify: "This is a legal-value parameter" + name it
Expert review determines: The exact constraint logic and encoding

---

CONDITIONAL PARAMETERS: WHEN THEY EXIST

Allen: "Sometimes a WARL field isn't explicitly labelled WARL, but become one 
under certain contexts (e.g a RW field may become RdOnly0, which means the 
set of legal values change."

Pattern:
- Field is RW under normal conditions → legal values {0, 1}
- Field becomes RdOnly0 under specific extensions → legal values {0}
- The shift in legal-value set makes it a parameter

Encoding: mask:value{;state} pattern with condition specified

---

PARAMETER IDENTIFICATION VS COMBINATION EXTRACTION

Allen: "I don't think we even care that an LLM extracts the valid combinations 
(though there should be code to validate it somewhere). We care that it 
identifies the legal parameter(s)."

This means:
- ✅ DO: Identify that a field has legal-value constraints
- ✅ DO: Identify which parameters control those constraints
- ✅ DO: Name the parameter and flag it for expert classification
- ❌ DON'T: Try to extract all valid combinations from prose
- ❌ DON'T: Claim to have solved the constraint logic

The constraint logic requires expert review and potentially formal specification.

---

ENCODING PRACTICAL GUIDANCE

Allen: "Having just one way to do it is advantageous, in my view, and I don't 
know how many cases where that second encoding actually gets used as it is 
only necessary when a legal value is >64."

Practical approach for Fall 2026:
1. Identify parameters (LLM task)
2. Classify into schema type (LLM + expert)
3. For enum: list the values (if <64) or use bitmask
4. For wider fields: use range or flag for expert review
5. For conditional: identify the condition, let expert formalize

Focus on the first step. Don't get stuck on encoding perfection.

---

WARL FIELDS: OBVIOUS STARTING POINT

Allen: "WARL are obvious cases. There aren't so many WARL fields (that are 
larger than a single bit, which is trivial to handle) that we can't fill in 
those details by hand if need be."

Strategy:
- Start with explicitly labeled WARL fields (obvious)
- Extend to conditionally-WARL fields (RdOnly0 cases)
- Hand-fill details for complex cases (18 undecidable)
- Don't try to automate 100% - 80-90% extraction + manual refinement is fine

---

SUMMARY FOR FALL 2026

Three-tier approach:
1. **Identify parameters** (automated LLM extraction)
   - What fields have legal-value constraints?
   - What parameters control those constraints?
   - Which are obviously WARL, which are conditional?

2. **Classify schema type** (LLM + expert review)
   - enum (1-64 values): list them
   - mask:value{;state}: identify condition
   - range_hi:range_lo: set bounds
   - conditional: flag for expert

3. **Validate & refine** (expert review)
   - Manual review for undecidable cases
   - Build validation code to check constraints
   - Refine based on spec text interpretation

This is grounded, defensible, and aligns with Allen's actual guidance.
